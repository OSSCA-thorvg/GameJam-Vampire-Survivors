# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

The rules and project skills in `.claude/` are shared with Codex. Codex starts with [`AGENTS.md`](AGENTS.md), which maps work stages to these files and supplies equivalents for Claude Code-only commands and tools. Those adapters preserve the shared checks and merge gates.

Keep this file current: any PR that changes commands, architecture, workflow, rules or skills updates it in the same PR (`.claude/rules/docs-sync.md`). CI fails if a rule or skill is not mentioned here.

## Getting started

For a new contributor in a fresh clone. Nothing here depends on a particular machine, account or plugin.

- **Prerequisites:** Git, nvm, Docker (Docker Desktop, OrbStack or Colima, running), the GitHub CLI `gh` logged in with your own account that has access to `OSSCA-thorvg/GameJam-Vampire-Survivors` (`gh auth status`, then `gh repo view OSSCA-thorvg/GameJam-Vampire-Survivors --json nameWithOwner`), and Claude Code. The `dw` plugin is optional.
- **First session:** `nvm use`, `corepack enable`, then `pnpm install`. The install also registers the pre-commit hook (`.git/hooks/pre-commit`), so there is no manual hook setup.
- **Pick work:** `gh issue list -R OSSCA-thorvg/GameJam-Vampire-Survivors --label status:ready`. Every `status:ready` issue meets the readiness standard (`.claude/rules/issues.md`): it says what to set up, read and run, so you can start without asking. `docs/roadmap.md` shows the order.
- **The loop:** `/issue-start #N` → implement → `/issue-finish`. `issue-finish` enables GitHub's native auto-merge, and GitHub merges the PR once the `main` ruleset's required checks pass.
- **When blocked:** comment on the issue saying what is missing, and label it `status:blocked` (`gh issue edit <N> -R OSSCA-thorvg/GameJam-Vampire-Survivors --remove-label status:in-progress --add-label status:blocked`).

## Project

A browser game in the style of Vampire Survivors, for single player and 2-player online versus play, rendered with ThorVG's `@thorvg/webcanvas`. The game's title is Crimson Vigil. Requirements are in `REQUIREMENTS.md`, written in Korean; ADRs cite its items by number. Every architectural choice is an ADR in `docs/adr/`. Read `docs/adr/README.md` first.

Current state: the toolchain exists (pnpm workspace with `@vs/client`, `@vs/server` and `@vs/shared`, lint, format, tests, the pre-commit hook and CI's `pnpm check`), and the client boots: the main thread transfers the canvas to the game worker, which runs ThorVG (`gl`) and the fixed-step loop (#2). The server speaks the full room protocol (#18). The title's Multiplayer button leads through the character select to a nickname and room-code entry and a lobby where two players meet, ready up and see the host's countdown (#19); the countdown starts a versus match: both play their own world from the match seed with a live opponent panel, the server decides Win, Lose or Draw, and Rematch returns to the same lobby (#20); during the match both worlds show side by side in two equal panes, the opponent's drawn from the relayed view stream (#114, #115). In versus matches enemies occasionally drop interference items (Swarm, Gem Thief, Elite Call) whose effect the server routes to an opponent's world, with a banner naming the sender (#21). During a match each page streams a quantized view of its own world to the opponent through the server, kept in the opponent's worker for the split panes that #115 draws (#114, ADR 0018). The manifest asset library, cached masters, loading progress and development gallery are available (#3), with the 84-ID generated pixel pack, 36 native motion assets and the protected font (#76/#84). The catalog also retains the shape-only performance fixture (#22). Entity stores, a spatial grid and reusable render pools are available with a numeric stress scene (#6). After loading, a title screen starts the run: the player walks in eight directions with a centred camera over the tiled ground (#7), enemies spawn from the wave table, chase him and keep apart (#8), and contact damage leads to death and a results screen with Retry and Title; Escape or a hidden tab pauses, and a ThorVG HUD shows HP, the timer and kills (#9). The player starts with the Whip, `G` (dev) grants the Magic Wand, and weapons damage, knock back and kill enemies, which raises the kill count (#10). Killed enemies drop XP gems that the player pulls in; a full XP bar pauses the run for a level-up choice of new or upgraded weapons and passives (#11). The 8 passive items change one shared player stat block that every system reads (#12). All 8 base weapons are playable to level 8: Knife, Axe, Cross, King Bible, Fire Wand and Garlic join the Whip and the Magic Wand (#13). Between the title and the run a character select offers Warden, Ember, Swift and Aurelia, each with its own starting weapon and stat modifiers (#14). Braziers around the player break under any weapon and drop Floor Chicken, Rosary, Orologion, Vacuum or Little Clover (#16). Bosses and elites drop treasure chests whose DOM overlay shows 1, 3 or 5 rewards, including the 8 evolutions from 5:00, and bosses are tethered to the player (#15). The run HUD lists the current weapons and passives with their levels at the upper left, and an elite or boss carrying a chest appears each full minute before the finale (#156). The stage is complete: 15 waves over six enemies, elites, swarms, `reaper5` at 5:00 and `reaper10` at 10:00; at 15:00 the screen clears and Death appears, and the results screen says "Stage cleared" or "Game over" with the character and each weapon's damage (#17). On every push to `main`, `deploy.yml` publishes the client to GitHub Pages; the owner builds the server's runtime image on their own host from a clone and runs it by hand, and its public domain is not set up yet (#23, #144, ADRs 0017 and 0023). A perf overlay (`?perf`, also in production) and named `?stress=<name>` scenarios measure frame timing; the measurements in `docs/reference/performance.md` keep the caps at 400/600/400 and answer the Lottie-per-enemy question (#22). Every boot first plays the 7-second "Powered by ThorVG" Lottie (`ui.splash`) in the worker while the rest of the assets load; the title follows once both are done, and a slower load holds the last frame with `Loading n/total` under the logo (#126, ADR 0020). The game has 17 synthesized sound effects (`sfx.*`) and 2 original music loops (`music.*`, stage 145 BPM in D minor, title 95 BPM in A minor) as committed MP3 assets rendered from `scripts/audio/sounds.json` with pinned ZzFX/ZzFXM (#128, ADR 0021). They play after the first key or click: the title loop on menus and the stage loop in runs, ducked under the pause and dialogs, the worker's hit, kill, gem and hurt cues and the main thread's menu, level-up, chest, death and interference cues; `M` or the corner button mutes and the pause screen sets the music and effects volume, saved in `localStorage` (#129). The splash stays silent. The stage is tuned for playability against a headless balance probe: every normal enemy is slower than every character, a live cap per wave (`maxAlive`) holds back the batches, contact damage is lower and `BASE_STATS` carries a built-in PowerUp equivalent (#148). Single-player runs leave personal records in the browser (`localStorage` `vs.records`, ADR 0022): "New best!" badges on the results, each character's best time and clear on its card, and a Records screen from the title with an in-page reset; versus matches are not recorded (#143). Phones and tablets play by touch in landscape: a floating joystick, a Pause button, tappable screens, no page scroll or zoom, sound on the first tap and a rotate hint in portrait (#149). Work is planned as GitHub issues in phases (`docs/roadmap.md`).

## Workflow (mandatory)

- **Problems found while implementing:**
  - Ask the user right away if the problem blocks the issue or needs a decision.
  - Otherwise, create a follow-up issue to the readiness standard (or comment on the existing issue that covers it), list it under `## Follow-ups` in the PR, and finish the current issue without widening it (`.claude/rules/issues.md`).
- **Prerequisite gate:** before starting an issue, `issue-start` checks its "Depends on" issues. If any is open, or an artifact it promised is missing on `main`, stop, comment, and set `status:blocked`. CI also fails a PR whose issue still has open dependencies.
- **Delegate to subagents by default** (requested by the user):
  - Implement each issue in a subagent, briefed with the issue body **and all its comments**, the ADRs it cites, and this file. Comments can change the plan, so the brief tells the subagent to read the thread in full and to re-read it before finishing.
  - Run independent issues (for example, parallel roadmap tracks) in parallel subagents, each briefed with the worktree path that `issue-start` created for its issue.
  - Delegate research, reviews and the `security-check` pass the same way.
  - The main session plans, briefs, verifies the subagent's result against the acceptance criteria, and runs `issue-finish`.
  - Only trivial lookups and single-file edits stay in the main session.

- **Every issue starts with `/issue-start #N`, and only with it** (requested by the user). It runs the prerequisite gate, sets the assignee and `status:in-progress`, creates the issue's own worktree at `.claude/worktrees/issue-<N>` (all work happens there), checks the scope, and posts the start comment with the `<!-- issue-start -->` marker. CI rejects a PR whose issue lacks an assignee or that marker. Do not start issues with `/dw:impl`, `/dw:ship` or a branch in the main checkout. The procedure lives in the skill; this file does not restate it.
- **Check the scope first, and run what you write (`.claude/rules/verification.md`).** `issue-start` runs `impact-check` in scope mode: what changes, who consumes it, and the one fact the change is safe because of. Every code change is then run in the real app (the browser for the client, the Docker container for the server), not just read or unit-tested. `issue-finish` runs `impact-check` in proof mode (safety fact proven by running code, level 4) and drives user-visible criteria in the running game (level 5) with `verify-game` (Claude in Chrome when the extension is connected, Playwright otherwise; CI's `verify` job runs the Playwright smoke journey). Evidence stays in the git-ignored `verification/` folder and is summarized in the PR's **Impact** and **Verification** sections.
- **Resolve conflicts by rebasing (`.claude/rules/conflicts.md`).** When `main` moved or a PR conflicts, run `resolve-conflicts`: back up, rebase onto `origin/main`, keep both sides' intent, check functional compatibility, propagate `main`'s improvements, squash back to one commit and `git push --force-with-lease`. The PR body records it under **Conflicts**.
- **Finish with `issue-finish`.** It verifies the acceptance criteria, runs `pnpm check`, brings a stale branch up to date, opens the PR and enables native auto-merge (`gh pr merge <PR> --auto --squash`). GitHub squash-merges it as soon as the ruleset's required checks pass, and `post-merge.yml` marks the issue `status:done`; `issue-finish` waits for the merge and verifies the result.
- Rules live in `.claude/rules/`:
  - `issues.md`
  - `commits.md`
  - `pull-requests.md`
  - `labels.md`
  - `security.md`
  - `docker.md`
  - `verification.md`: scope checks before coding, running every change, proof levels and evidence
  - `conflicts.md`: rebasing onto `main` and the fixed resolutions per file kind
  - `docs-sync.md`: which docs to update with which change, including this file

  Read the matching file before creating an issue, committing (use the `commit` skill), or opening a PR.

- New issues go through `issue-create`; each needs a detailed **Implementation plan** section. Labels come from `.github/labels.json`, synced with `label-sync`; their meanings are in `.claude/rules/labels.md`.
- A decision that binds later work gets an ADR through `adr-new` in the same PR. Do not contradict an accepted ADR. Supersede it.
- The project's rules and skills are complete on their own; the `dw` plugin is not needed. Its label, branch, commit and `gh` conventions are restated in `.claude/rules/labels.md`, `commits.md` and `pull-requests.md`. Even if the dw plugin is installed, do not use its workflow skills (`/dw:impl`, `/dw:ship`, `/dw:epic-impl` and similar) for this repository's issues: issue work starts only with `issue-start` and merges only through native auto-merge enabled by `issue-finish`.
- Commit, PR and issue text is written in English with a `feat:`/`fix:`/`update:`/`refactor:`/`test:`/`docs:`/`chore:` subject. PR titles carry no `(#N)` suffix: GitHub appends the PR number to the squash commit, and the issue link is `Closes #N` in the body. Paragraphs are not hard-wrapped, and bodies are passed with `--body-file`. Do not add AI attribution or `Co-Authored-By` trailers.
- The pre-commit hook (ADR 0002, `lint-staged.config.js`) runs Prettier and ESLint on staged files, then the Vitest tests related to the staged code files (`vitest related`), and the whole `@vs/shared` project when a file under `assets/` is staged; it must pass. Locally only related tests run (`pnpm test:changed` while iterating); `pnpm check` and CI keep running the full suite (user decision, 2026-11-08). Never commit with `--no-verify`. If the hook fails, fix the code and commit again.
- **Security (ADR 0011):**
  - Follow `.claude/rules/security.md`.
  - Packages install only versions at least 7 days old (`minimumReleaseAge`), and dependency build scripts are blocked unless listed in `allowBuilds`.
  - Run the `security-check` skill before PRs touching dependencies, the server, the protocol, Docker, CI or user-data rendering.
- **Linear history (ADR 0015, unchanged from 0012):** a PR branch is one commit rebased onto the current `origin/main`, with the PR title as subject; squash merges only. Work-in-progress commits are fine locally; squash before pushing and after every fix, then `git push --force-with-lease` (never plain `--force`, never on `main`). Never create merge commits: each clone sets `pull.rebase true` and `merge.ff only` (`issue-start`). CI rejects a branch with more than one commit or behind `main`, and the ruleset requires linear history and an up-to-date branch.
- Stage files by path. Never use `git add -A`, `git add .`, `git stash` or `git clean` on the user's working tree.
- Always pass `--json <fields>` to `gh issue view` and `gh pr view`. Change labels with `gh issue edit`, which also works on PRs.
- GitHub repo: `OSSCA-thorvg/GameJam-Vampire-Survivors` (private). Each contributor runs `gh` with their own account that has access to the repo (`gh auth status`). If `gh` reports the repo is not found (404 or "Could not resolve"), the active account lacks access: stop and ask the user. Do not switch accounts or borrow credentials. If `gh pr edit` or `gh issue edit` fails with a missing-scope error (such as `read:org`), make the same change with `gh api` REST calls (`gh api -X PATCH repos/OSSCA-thorvg/GameJam-Vampire-Survivors/pulls/<PR> -f title=...`, or `.../issues/<N>/labels`); `.claude/rules/pull-requests.md` § Using `gh` lists them.
- Issues use the template in `issue-create` (mirrored in `.github/ISSUE_TEMPLATE/task.md`); PRs use `.github/pull_request_template.md`.
- **Merging (ADR 0015):** the `main` ruleset (`.github/rulesets/main.json`, applied by a maintainer with `scripts/github/apply-ruleset.sh`) requires a PR, the five CI checks (`pnpm check`, `verify`, `repo rules`, `server image`, `PR rules`) green on an up-to-date branch, linear history and squash merges, and forbids force-pushes and deletion; nobody, admins included, can bypass it. `issue-finish` enables native auto-merge with `gh pr merge <PR> --auto --squash`, the only merge command anyone runs; never merge immediately (`gh pr merge` without `--auto`) and never use the web UI merge button. The hold is auto-merge off (`gh pr merge <PR> --disable-auto`); a `status:blocked` label on a PR is only a visible marker. `.github/workflows/pr-feedback.yml` comments on red or stale PRs and never merges; `.github/workflows/post-merge.yml` labels the issue `status:done` and unblocks dependents. Renaming a CI job means updating the ruleset JSON (`check-ruleset.mjs` in `repo rules` fails otherwise) and re-running `apply-ruleset.sh` (`.claude/rules/pull-requests.md`).

## Architecture

Read the ADR for the full reasoning.

- **Monorepo (ADR 0002):**
  - `packages/client` (`@vs/client`) is the Vite app with no UI framework (ADR 0009); its only runtime dependency is `@thorvg/webcanvas` (ADR 0011). `src/main` and `src/worker` are type-checked against DOM and WebWorker libs by separate tsconfigs (`tsconfig.main.json`, `tsconfig.worker.json`);

- **Threads (ADR 0004):** the main thread (`client/src/main/`) owns the DOM UI, keyboard capture and the WebSocket. A dedicated module worker (`client/src/worker/`) owns the simulation and all ThorVG rendering, including the HUD, on an `OffscreenCanvas` transferred at startup. The two talk only through the typed messages in `client/src/protocol/worker-messages.ts`; `init` and `resize` carry the pane `layout` (`'single' | 'columns' | 'rows'`, #115) and `opponentState` (`'live' | 'away' | 'out'`) dims the opponent pane. Nothing in the worker may touch the DOM; nothing on the main thread may touch the canvas. A worker `error` event before its `ready` message is a boot failure and replaces the page with "The game could not start."; after `ready`, `main/runtime-error.ts` (`routeWorkerError`, `createRuntimeErrorReporter`) logs `[vs] game worker runtime error: …` and appends a non-blocking `#runtime-error` notice with Reload and Dismiss to `<body>`, leaving the screens mounted (#123). An exception in a loop step or render still stops `worker/loop.ts` for good, so the notice asks for a reload.
- **Rendering (ADR 0003):**
  - Initialize ThorVG once with `renderer: 'gl'`.
  - Paints are created once and pooled, cloned with `duplicate()` from a loaded master. Per frame, only transforms, visibility and opacity change, followed by one `canvas.update()` and one `canvas.render()`.
  - Never create or dispose Paints per frame.
  - Do not use the `/thread` build.
  - Panes (#115, ADR 0018): the game view draws under `render/panes.ts` `createPanes(TVG, root)`: `self` (clipped by its own rectangle) holds the own world's layers, the defeat overlay and the "YOU" label (`render/pane-hud.ts`, shown only with two panes); an untransformed clipped frame holds the translated `opponent` scene (ThorVG did not move a scene's clipper with that scene's translate, so every clip sits in `root` units). `?gallery`, `?stress` and the perf overlay stay on `root`. Since #126 the panes sit under a `gameRoot` scene, and the boot splash (`render/splash.ts`) draws above them on a `splashLayer`. The opponent pane (`worker/game/opponent-view.ts` `createOpponentView`) creates all its paints at boot in its own pools and never acquires past their prewarm: `VIEW_ENEMY_MAX` (160) per normal enemy type (`BOSS_POOL_PREWARM` for bosses), `VIEW_GEM_MAX` (48) per gem tier, `VIEW_PICKUP_MAX` (8) per pickup pool, one sprite per character, the HP bar; it draws the feed 200 ms behind (`OPPONENT_RENDER_DELAY_MS`), interpolating only the player. `createOpponentHud` adds "OPPONENT", the opponent's `mm:ss` and the "AWAY" (60%) / "OUT" (40%) dim; all ThorVG text is printable ASCII.
  - `worker/render/thorvg.ts` `initThorVG` returns `{ TVG, canvas, root }`; later layers go under the scaled `root` scene. `thorvg.wasm` is served from `/thorvg/thorvg.wasm` by the `copyThorvgWasm` plugin in `vite.config.ts`.
  - Every ThorVG `Text` uses `text.font(HUD_FONT)`, read after `initThorVG` resolves (ADR 0013). `initThorVG` resolves `font.hud` through the already validated asset manifest and fetches its `fonts/hud.ttf` file (`assets/fonts/hud.ttf`, asset ID `font.hud`: Noto Sans Mono Regular subset to printable ASCII `U+0020`–`U+007E`, OFL, under 15 KB) and registers it as `'hud'`; if that fails it logs one warning and `HUD_FONT` stays `'default'`, the built-in font, which lacks `:`, `/`, `%` and most punctuation. ThorVG text stays printable ASCII (numbers, English labels); Korean text and every nickname are DOM text set with `textContent` (ADR 0009). Rebuild the subset only with `scripts/make-hud-font.sh`.
  - Production builds remove only the unused `assets/thorvg-*.wasm` copy through `removeDuplicateThorvgWasm`. `src/build.test.ts` checks the real output with `vitest.build.config.ts` after `pnpm build`; ordinary unit tests exclude it through `vitest.config.ts`.

- **Simulation (ADR 0004):**
  - Fixed 60 Hz step with an accumulator, at most 5 steps per frame.
  - In a hidden tab, a `setTimeout` loop keeps simulating without rendering (cap of 120 steps per tick). In single player, hiding the tab pauses the game instead.
  - The view is a fixed 1280×720 logical area, letterboxed. `main/viewport.ts` sizes the canvas in whole device pixels and fills an axis whose letterbox would be under 2 device pixels (#103). In a versus match `computeViewport(w, h, dpr, 2)` fits two such views with a 16-unit gap (`PANE_GAP`): `columns` when `min(W / 2576, H / 720) >= min(W / 1280, H / 1456)`, else `rows` (ADR 0018), returning `layout` and the pane rects; one pane is unchanged.
  - Typed-array struct-of-arrays plus a uniform-grid spatial hash.
  - No per-entity allocation in the frame loop.
  - All randomness comes from the seeded PRNG: `createRng(seed)` in `shared/src/random.ts` (mulberry32; `next`, `range`, `int`, `pick`), with `rng.fork(label)` giving each system its own stream. Never `Math.random()`.
  - Runs (#9): `worker/game/view.ts` `createGameView` creates every run's paints once at boot (ground, player, enemy pools, HUD in `render/hud.ts`); `game/session.ts` `createSession` swaps worlds on it for `startRun`/`endRun` with `releaseAll()` and `Store.clear()`, never creating or disposing a Paint (`session.test.ts`). `world.events` (`game/events.ts`) is a fixed 1024-record queue cleared before the first system of every step, so an event lives for exactly one step; systems `push(kind)` and fill the returned record (`playerHit` from #9, `enemyKilled` from #10). `world.state` becomes `'dead'` at 0 HP, after which the world no longer steps; `world.stats` (`timeSec`, `kills`, `level`) feeds the results. Gameplay constants (`BASE_MAX_HP`, `PLAYER_RADIUS`, `HIT_INVULN_SEC`, `MAX_ENEMY_RADIUS`) are in `shared/src/content/constants.ts`.
  - `worker/loop.ts` `createLoop` implements the step, the hidden-tab policy (`setBackgroundPolicy('pause' | 'simulate')`, default `'pause'`) and `fastForward`; constants are in `worker/constants.ts`. It never runs more than `MAX_STEPS` per visible frame and never renders while hidden (`loop.test.ts`).
  - The run is a `World` (`worker/game/world.ts`, #7): `createWorld({ seed, characterId, view })` owns all run state (`player`, `camera`, `time`, `input`, the root `rng`). `world.step(dt)` runs the systems in the order of the exported `SYSTEMS` array in `world.ts` (now `inputSystem`, `playerMovementSystem`, `cameraSystem`, `spawnerSystem`, `enemyMovementSystem`, `enemyRelocateSystem`, `contactDamageSystem`, `weaponSystem`, `projectileSystem`, `fxSystem`, `cleanupSystem`); a later issue inserts its system at the position it states, never calls one directly. Each system forks its own named RNG stream from `world.rng` (`world.rng.fork('spawn')`) and never draws from the root, so one system's draws never shift another's. `world.render(alpha)` translates the `world` layer by the camera (snapped to device pixels), syncs the ground, the enemies, then the player; the worker then calls `canvas.update()`/`render()` once.
  - The camera keeps the player exactly centred (`worker/game/camera.ts`; `camera.viewRect(margin)` for spawning and culling). The ground (`worker/render/ground.ts`) is a fixed 13 × 9 grid of pooled `stage.ground` tiles (anchor `[0, 0]`) that starts one tile before the view, so pixel snapping and the canvas fill (#103) never uncover an edge, repositioned only when the camera crosses a tile and overlapping by 1 unit (scale 129/128) so no seams show. Movement speed is `BASE_MOVE_SPEED` (`shared/src/content/constants.ts`); diagonals are normalized. The worker creates the world after the assets load (seed `Date.now() >>> 0`, `'warden'`) except in `?gallery` and `?stress`; #9 replaces this auto-start.
  - Enemies (#8): `worker/game/enemies.ts` holds the enemy store (`world.enemies`, capacity `ENEMY_CAP`; columns `x`, `y`, `vx`, `vy`, `hp`, `type` indexing `ENEMY_LIST`, `kbX`/`kbY`/`kbTime`/`flash` written by #10's combat, `flags` with bit 0 boss and bit 1 dead (`ENEMY_FLAG_DEAD`), `flip`, `shownOpacity`, plus the render binding), one `PaintPool` per enemy asset in the `enemies` layer (200 prewarmed each), `world.enemyGrid` and `spawnEnemy(world, enemyId, x, y)` (-1 at the cap). `systems/spawner.ts` follows `STAGE.waves` (batch every `spawnIntervalSec`, skipped while `maxAlive` or more enemies that are neither bosses nor elites live (#148), top-up to `minAlive`, at most 20 per step, never past the cap, a dev assertion after it) on the perimeter of `camera.viewRect(64)`, drawing only from `world.spawnRng` (`rng.fork('spawn')`), so both players of a match face the same schedule. `systems/enemy-movement.ts` rebuilds the grid once per step, then chases the player with separation (or follows knockback while `kbTime > 0`); `systems/enemy-relocate.ts` moves non-boss enemies beyond 1360 units to the ring ahead of the player every 0.5 s, from `rng.fork('relocate')`. Snapshot fields `enemies` (count) and `enemyPositions` (`[uid, type, x, y]`); `determinism.test.ts` proves the same seed gives the same positions.

Snapshot fields `projectiles` (count) and `weapons` (`{ id, level }[]`); `kills` rises. A weapon with `activeLeft > 0` (books out) holds its cooldown. Base and evolved attacks use `WeaponContext.attackY` at the torso (#157). The Garlic and Soul Eater paints share its `playerAttackY` calculation. The player position remains anchored at the feet.

- **XP and level-up (#11, ADRs 0004, 0008):** `gemDropSystem`, `gemSystem` and `levelSystem` run right after `cleanupSystem`. ## Gameplay fidelity

Before implementing or tuning gameplay, read the matching section of `docs/reference/gameplay.md` and compare with footage of the original game, linked there.
