# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

The rules and project skills in `.claude/` are shared with Codex. Codex starts with [`AGENTS.md`](AGENTS.md), which maps work stages to these files and supplies equivalents for Claude Code-only commands and tools. Those adapters preserve the shared checks and merge gates.

Keep this file current: any PR that changes commands, architecture, workflow, rules or skills updates it in the same PR (`.claude/rules/docs-sync.md`). CI fails if a rule or skill is not mentioned here.

## Getting started

For a new contributor in a fresh clone. Nothing here depends on a particular machine, account or plugin.

- **Prerequisites:** Git, nvm, Docker (Docker Desktop, OrbStack or Colima, running), the GitHub CLI `gh` logged in with your own account that has access to `OSSCA-thorvg/GameJam-Vampire-Survivors` (`gh auth status`, then `gh repo view OSSCA-thorvg/GameJam-Vampire-Survivors --json nameWithOwner`), and Claude Code. The `dw` plugin is optional.
- **First session:** `nvm use`, `corepack enable`, then `pnpm install`. The install also registers the pre-commit hook (`.git/hooks/pre-commit`), so there is no manual hook setup.
- **Pick work:** `gh issue list -R OSSCA-thorvg/GameJam-Vampire-Survivors --label status:ready`. Every `status:ready` issue meets the readiness standard (`.claude/rules/issues.md`): it says what to set up, read and run, so you can start without asking. `docs/roadmap.md` shows the order.
- **The loop:** `/issue-start #N` → implement → `/issue-finish`. `issue-finish` enables GitHub's native auto-merge, and GitHub merges the PR once the `main` ruleset's required checks pass.
- **When blocked:** comment on the issue saying what is missing, and label it `status:blocked` (`gh issue edit <N> -R OSSCA-thorvg/GameJam-Vampire-Survivors --remove-label status:in-progress --add-label status:blocked`).

## Project

A browser game in the style of Vampire Survivors, for single player and 2-player online versus play, rendered with ThorVG's `@thorvg/webcanvas`. Requirements are in `REQUIREMENTS.md`, written in Korean; ADRs cite its items by number. Every architectural choice is an ADR in `docs/adr/`. Read `docs/adr/README.md` first.

Current state: the toolchain exists (pnpm workspace with `@vs/client`, `@vs/server` and `@vs/shared`, lint, format, tests, the pre-commit hook and CI's `pnpm check`), and the client boots: the main thread transfers the canvas to the game worker, which runs ThorVG (`gl`) and the fixed-step loop (#2). The server speaks the full room protocol (#18), with no client UI for it yet. The manifest asset library, cached masters, loading progress and development gallery are available (#3), with the84-ID generated pixel pack, cached image-backed Lottie and the protected font (#76). Entity stores, a spatial grid and reusable render pools are available with a numeric stress scene (#6). After loading, a title screen starts the run: the player walks in eight directions with a centred camera over the tiled ground (#7), enemies spawn from the wave table, chase him and keep apart (#8), and contact damage leads to death and a results screen with Retry and Title; Escape or a hidden tab pauses, and a ThorVG HUD shows HP, the timer and kills (#9). The player starts with the Whip, `G` (dev) grants the Magic Wand, and weapons damage, knock back and kill enemies, which raises the kill count (#10). Killed enemies drop XP gems that the player pulls in; a full XP bar pauses the run for a level-up choice of new or upgraded weapons (#11). Work is planned as GitHub issues in phases (`docs/roadmap.md`).

## Workflow (mandatory)

- **Problems found while implementing:**
  - Ask the user right away if the problem blocks the issue or needs a decision.
  - Otherwise, create a follow-up issue to the readiness standard (or comment on the existing issue that covers it), list it under `## Follow-ups` in the PR, and finish the current issue without widening it (`.claude/rules/issues.md`).
- **Prerequisite gate:** before starting an issue, `issue-start` checks its "Depends on" issues. If any is open, or an artifact it promised is missing on `main`, stop, comment, and set `status:blocked`. CI also fails a PR whose issue still has open dependencies.
- **Delegate to subagents by default** (requested by the user):
  - Implement each issue in a subagent, briefed with the issue body **and all its comments**, the ADRs it cites, and this file. Comments can change the plan, so the brief tells the subagent to read the thread in full and to re-read it before finishing.
  - Run independent issues (for example, parallel roadmap tracks) in parallel subagents, each briefed with the worktree path that `issue-start` created for its issue.
  - Delegate research, reviews and the `security-check` pass the same way.
  - The main session plans, briefs, verifies the subagent's result against the acceptance criteria, and runs `issue-finish`.
  - Only trivial lookups and single-file edits stay in the main session.

- **Every issue starts with `/issue-start #N`, and only with it** (requested by the user). It runs the prerequisite gate, sets the assignee and `status:in-progress`, creates the issue's own worktree at `.claude/worktrees/issue-<N>` (all work happens there), checks the scope, and posts the start comment with the `<!-- issue-start -->` marker. CI rejects a PR whose issue lacks an assignee or that marker. Do not start issues with `/dw:impl`, `/dw:ship` or a branch in the main checkout. The procedure lives in the skill; this file does not restate it.
- **Check the scope first, and run what you write (`.claude/rules/verification.md`).** `issue-start` runs `impact-check` in scope mode: what changes, who consumes it, and the one fact the change is safe because of. Every code change is then run in the real app (the browser for the client, the Docker container for the server), not just read or unit-tested. `issue-finish` runs `impact-check` in proof mode (safety fact proven by running code, level 4) and drives user-visible criteria in the running game (level 5) with `verify-game` (Claude in Chrome when the extension is connected, Playwright otherwise; CI's `verify` job runs the Playwright smoke journey). Evidence stays in the git-ignored `verification/` folder and is summarized in the PR's **Impact** and **Verification** sections.
- **Resolve conflicts by rebasing (`.claude/rules/conflicts.md`).** When `main` moved or a PR conflicts, run `resolve-conflicts`: back up, rebase onto `origin/main`, keep both sides' intent, check functional compatibility, propagate `main`'s improvements, squash back to one commit and `git push --force-with-lease`. The PR body records it under **Conflicts**.
- **Finish with `issue-finish`.** It verifies the acceptance criteria, runs `pnpm check`, brings a stale branch up to date, opens the PR and enables native auto-merge (`gh pr merge <PR> --auto --squash`). GitHub squash-merges it as soon as the ruleset's required checks pass, and `post-merge.yml` marks the issue `status:done`; `issue-finish` waits for the merge and verifies the result.
- Rules live in `.claude/rules/`:
  - `issues.md`
  - `commits.md`
  - `pull-requests.md`
  - `labels.md`
  - `security.md`
  - `docker.md`
  - `verification.md`: scope checks before coding, running every change, proof levels and evidence
  - `conflicts.md`: rebasing onto `main` and the fixed resolutions per file kind
  - `docs-sync.md`: which docs to update with which change, including this file

  Read the matching file before creating an issue, committing (use the `commit` skill), or opening a PR.

- New issues go through `issue-create`; each needs a detailed **Implementation plan** section. Labels come from `.github/labels.json`, synced with `label-sync`; their meanings are in `.claude/rules/labels.md`.
- A decision that binds later work gets an ADR through `adr-new` in the same PR. Do not contradict an accepted ADR. Supersede it.
- The project's rules and skills are complete on their own; the `dw` plugin is not needed. Its label, branch, commit and `gh` conventions are restated in `.claude/rules/labels.md`, `commits.md` and `pull-requests.md`. Even if the dw plugin is installed, do not use its workflow skills (`/dw:impl`, `/dw:ship`, `/dw:epic-impl` and similar) for this repository's issues: issue work starts only with `issue-start` and merges only through native auto-merge enabled by `issue-finish`.
- Commit, PR and issue text is written in English with a `feat:`/`fix:`/`update:`/`refactor:`/`test:`/`docs:`/`chore:` subject. PR titles carry no `(#N)` suffix: GitHub appends the PR number to the squash commit, and the issue link is `Closes #N` in the body. Paragraphs are not hard-wrapped, and bodies are passed with `--body-file`. Do not add AI attribution or `Co-Authored-By` trailers.
- The pre-commit hook (ADR 0002, `lint-staged.config.js`) runs Prettier and ESLint on staged files, then the Vitest tests related to the staged code files (`vitest related`), and the whole `@vs/shared` project when a file under `assets/` is staged; it must pass. Locally only related tests run (`pnpm test:changed` while iterating); `pnpm check` and CI keep running the full suite (user decision, 2026-11-08). Never commit with `--no-verify`. If the hook fails, fix the code and commit again.
- **Security (ADR 0011):**
  - Follow `.claude/rules/security.md`.
  - Packages install only versions at least 7 days old (`minimumReleaseAge`), and dependency build scripts are blocked unless listed in `allowBuilds`.
  - Run the `security-check` skill before PRs touching dependencies, the server, the protocol, Docker, CI or user-data rendering.
- **Linear history (ADR 0015, unchanged from 0012):** a PR branch is one commit rebased onto the current `origin/main`, with the PR title as subject; squash merges only. Work-in-progress commits are fine locally; squash before pushing and after every fix, then `git push --force-with-lease` (never plain `--force`, never on `main`). Never create merge commits: each clone sets `pull.rebase true` and `merge.ff only` (`issue-start`). CI rejects a branch with more than one commit or behind `main`, and the ruleset requires linear history and an up-to-date branch.
- Stage files by path. Never use `git add -A`, `git add .`, `git stash` or `git clean` on the user's working tree.
- Always pass `--json <fields>` to `gh issue view` and `gh pr view`. Change labels with `gh issue edit`, which also works on PRs.
- GitHub repo: `OSSCA-thorvg/GameJam-Vampire-Survivors` (private). Each contributor runs `gh` with their own account that has access to the repo (`gh auth status`). If `gh` reports the repo is not found (404 or "Could not resolve"), the active account lacks access: stop and ask the user. Do not switch accounts or borrow credentials. If `gh pr edit` or `gh issue edit` fails with a missing-scope error (such as `read:org`), make the same change with `gh api` REST calls (`gh api -X PATCH repos/OSSCA-thorvg/GameJam-Vampire-Survivors/pulls/<PR> -f title=...`, or `.../issues/<N>/labels`); `.claude/rules/pull-requests.md` § Using `gh` lists them.
- Issues use the template in `issue-create` (mirrored in `.github/ISSUE_TEMPLATE/task.md`); PRs use `.github/pull_request_template.md`.
- **Merging (ADR 0015):** the `main` ruleset (`.github/rulesets/main.json`, applied by a maintainer with `scripts/github/apply-ruleset.sh`) requires a PR, the five CI checks (`pnpm check`, `verify`, `repo rules`, `server image`, `PR rules`) green on an up-to-date branch, linear history and squash merges, and forbids force-pushes and deletion; nobody, admins included, can bypass it. `issue-finish` enables native auto-merge with `gh pr merge <PR> --auto --squash`, the only merge command anyone runs; never merge immediately (`gh pr merge` without `--auto`) and never use the web UI merge button. The hold is auto-merge off (`gh pr merge <PR> --disable-auto`); a `status:blocked` label on a PR is only a visible marker. `.github/workflows/pr-feedback.yml` comments on red or stale PRs and never merges; `.github/workflows/post-merge.yml` labels the issue `status:done` and unblocks dependents. Renaming a CI job means updating the ruleset JSON (`check-ruleset.mjs` in `repo rules` fails otherwise) and re-running `apply-ruleset.sh` (`.claude/rules/pull-requests.md`).

## Architecture

Read the ADR for the full reasoning.

- **Monorepo (ADR 0002):**
  - `packages/client` (`@vs/client`) is the Vite app with no UI framework (ADR 0009); its only runtime dependency is `@thorvg/webcanvas` (ADR 0011). `src/main` and `src/worker` are type-checked against DOM and WebWorker libs by separate tsconfigs (`tsconfig.main.json`, `tsconfig.worker.json`);
  - `packages/server` (`@vs/server`) is the Node + `ws` relay, run in Docker (ADR 0010: `packages/server/Dockerfile`, `compose.yaml`); `GET /healthz` answers `ok`, WebSocket upgrades on `/ws` are accepted only from `ALLOWED_ORIGINS`, and `src/config.ts` reads `PORT` (8787), `LOG_LEVEL`, `ALLOWED_ORIGINS`, `TRUST_PROXY` and the test-only `MATCH_TIME_LIMIT_S_OVERRIDE`, honoured only when `NODE_ENV=test` (`.env.example`); `src/log.ts` writes JSON lines, never message bodies, nicknames or IPs; the modules are listed under Multiplayer below;
  - `packages/shared` (`@vs/shared`) holds protocol types and content data, with no DOM, worker or Node APIs; TypeScript, Vitest, the server's dev container (`development` condition) and the client (a Vite alias) read `src/index.ts`, while the runtime image runs the compiled `dist` (`default` condition);
  - the root `tsconfig.json` references every package, so `tsc -b` checks them all; `eslint.config.js`, `.prettierrc.json`, `lint-staged.config.js` (the pre-commit tasks) and `vitest.config.ts` (projects `packages/*`, plus the root-anchored `forceRerunTriggers` for `--changed` and `related`) live at the root;
  - `assets/` holds the art and `manifest.json`.
  - The browser favicon is `assets/ui/favicon.svg` (`ui.favicon`, cataloged as a placeholder), linked from `client/index.html` and served through Vite's `publicDir` in dev and production.
- **Threads (ADR 0004):** the main thread (`client/src/main/`) owns the DOM UI, keyboard capture and the WebSocket. A dedicated module worker (`client/src/worker/`) owns the simulation and all ThorVG rendering, including the HUD, on an `OffscreenCanvas` transferred at startup. The two talk only through the typed messages in `client/src/protocol/worker-messages.ts`. Nothing in the worker may touch the DOM; nothing on the main thread may touch the canvas.
- **Rendering (ADR 0003):**
  - Initialize ThorVG once with `renderer: 'gl'`.
  - Paints are created once and pooled, cloned with `duplicate()` from a loaded master. Per frame, only transforms, visibility and opacity change, followed by one `canvas.update()` and one `canvas.render()`.
  - Never create or dispose Paints per frame.
  - Do not use the `/thread` build.
  - `worker/render/thorvg.ts` `initThorVG` returns `{ TVG, canvas, root }`; later layers go under the scaled `root` scene. `thorvg.wasm` is served from `/thorvg/thorvg.wasm` by the `copyThorvgWasm` plugin in `vite.config.ts`.
  - Every ThorVG `Text` uses `text.font(HUD_FONT)`, read after `initThorVG` resolves (ADR 0013). `initThorVG` resolves `font.hud` through the already validated asset manifest and fetches its `fonts/hud.ttf` file (`assets/fonts/hud.ttf`, asset ID `font.hud`: Noto Sans Mono Regular subset to printable ASCII `U+0020`–`U+007E`, OFL, under 15 KB) and registers it as `'hud'`; if that fails it logs one warning and `HUD_FONT` stays `'default'`, the built-in font, which lacks `:`, `/`, `%` and most punctuation. ThorVG text stays printable ASCII (numbers, English labels); Korean text and every nickname are DOM text set with `textContent` (ADR 0009). Rebuild the subset only with `scripts/make-hud-font.sh`.
  - Production builds remove only the unused `assets/thorvg-*.wasm` copy through `removeDuplicateThorvgWasm`. `src/build.test.ts` checks the real output with `vitest.build.config.ts` after `pnpm build`; ordinary unit tests exclude it through `vitest.config.ts`.
- **Engine primitives (#6, ADRs 0003, 0004, 0007):**
  - `worker/ecs/store.ts` preallocates typed-array columns and sparse stable UIDs, swap-removes slots and retires an ID index at generation exhaustion. `ecs/spatial-grid.ts` hashes world cells; queries use caller-owned buffers and a bounded direct scan when the fixed key scratch cannot cover a large query.
  - `render/layers.ts` creates ordered world layers and a camera-independent HUD. `render/pool.ts` exports `PaintPool` and `RenderBinding`: pool releases hide instances without unregistering Lottie playback; bindings keep actual handles in their columns and follow store swaps. Unbind before ordinary removal; reset a run with all pools' `releaseAll()` followed by store `clear()`.
  - `shared/src/content/constants.ts` exports the initial `ENEMY_CAP`, `PROJECTILE_CAP` and `GEM_CAP`. Worker/shared code cannot call `Math.random`; ESLint requires `createRng`.
  - Dev/perf `?stress=3000` prewarms bat paints, moves/separates entities and replaces up to 1000 every 2 simulated seconds. Dev/e2e snapshots expose `debug.entities`, `paintsCreated`, `visiblePaints` and `churnCycles`; the overlay reads actual pool counters. Invalid named scenarios warn and fall back to the normal scene. Gallery takes precedence when both flags are set. Normal production excludes stress; the `perf` build retains it. Pinned ThorVG transform wrappers allocate transient views internally; pool reuse does not claim an allocation-free dependency stack.
- **Simulation (ADR 0004):**
  - Fixed 60 Hz step with an accumulator, at most 5 steps per frame.
  - In a hidden tab, a `setTimeout` loop keeps simulating without rendering (cap of 120 steps per tick). In single player, hiding the tab pauses the game instead.
  - The view is a fixed 1280×720 logical area, letterboxed.
  - Typed-array struct-of-arrays plus a uniform-grid spatial hash.
  - No per-entity allocation in the frame loop.
  - All randomness comes from the seeded PRNG: `createRng(seed)` in `shared/src/random.ts` (mulberry32; `next`, `range`, `int`, `pick`), with `rng.fork(label)` giving each system its own stream. Never `Math.random()`.
  - Runs (#9): `worker/game/view.ts` `createGameView` creates every run's paints once at boot (ground, player, enemy pools, HUD in `render/hud.ts`); `game/session.ts` `createSession` swaps worlds on it for `startRun`/`endRun` with `releaseAll()` and `Store.clear()`, never creating or disposing a Paint (`session.test.ts`). `world.events` (`game/events.ts`) is a fixed 1024-record queue cleared before the first system of every step, so an event lives for exactly one step; systems `push(kind)` and fill the returned record (`playerHit` from #9, `enemyKilled` from #10). `world.state` becomes `'dead'` at 0 HP, after which the world no longer steps; `world.stats` (`timeSec`, `kills`, `level`) feeds the results. Gameplay constants (`BASE_MAX_HP`, `PLAYER_RADIUS`, `HIT_INVULN_SEC`, `MAX_ENEMY_RADIUS`) are in `shared/src/content/constants.ts`.
  - `worker/loop.ts` `createLoop` implements the step, the hidden-tab policy (`setBackgroundPolicy('pause' | 'simulate')`, default `'pause'`) and `fastForward`; constants are in `worker/constants.ts`. It never runs more than `MAX_STEPS` per visible frame and never renders while hidden (`loop.test.ts`).
  - The run is a `World` (`worker/game/world.ts`, #7): `createWorld({ seed, characterId, view })` owns all run state (`player`, `camera`, `time`, `input`, the root `rng`). `world.step(dt)` runs the systems in the order of the exported `SYSTEMS` array in `world.ts` (now `inputSystem`, `playerMovementSystem`, `cameraSystem`, `spawnerSystem`, `enemyMovementSystem`, `enemyRelocateSystem`, `contactDamageSystem`, `weaponSystem`, `projectileSystem`, `fxSystem`, `cleanupSystem`); a later issue inserts its system at the position it states, never calls one directly. Each system forks its own named RNG stream from `world.rng` (`world.rng.fork('spawn')`) and never draws from the root, so one system's draws never shift another's. `world.render(alpha)` translates the `world` layer by the camera (snapped to device pixels), syncs the ground, the enemies, then the player; the worker then calls `canvas.update()`/`render()` once.
  - The camera keeps the player exactly centred (`worker/game/camera.ts`; `camera.viewRect(margin)` for spawning and culling). The ground (`worker/render/ground.ts`) is a fixed 12 × 8 grid of pooled `stage.ground` tiles (anchor `[0, 0]`), repositioned only when the camera crosses a tile and overlapping by 1 unit (scale 129/128) so no seams show. Movement speed is `BASE_MOVE_SPEED` (`shared/src/content/constants.ts`); diagonals are normalized. The worker creates the world after the assets load (seed `Date.now() >>> 0`, `'warden'`) except in `?gallery` and `?stress`; #9 replaces this auto-start.
  - Enemies (#8): `worker/game/enemies.ts` holds the enemy store (`world.enemies`, capacity `ENEMY_CAP`; columns `x`, `y`, `vx`, `vy`, `hp`, `type` indexing `ENEMY_LIST`, `kbX`/`kbY`/`kbTime`/`flash` written by #10's combat, `flags` with bit 0 boss and bit 1 dead (`ENEMY_FLAG_DEAD`), `flip`, `shownOpacity`, plus the render binding), one `PaintPool` per enemy asset in the `enemies` layer (200 prewarmed each), `world.enemyGrid` and `spawnEnemy(world, enemyId, x, y)` (-1 at the cap). `systems/spawner.ts` follows `STAGE.waves` (batch every `spawnIntervalSec`, top-up to `minAlive`, at most 20 per step, never past the cap, a dev assertion after it) on the perimeter of `camera.viewRect(64)`, drawing only from `world.spawnRng` (`rng.fork('spawn')`), so both players of a match face the same schedule. `systems/enemy-movement.ts` rebuilds the grid once per step, then chases the player with separation (or follows knockback while `kbTime > 0`); `systems/enemy-relocate.ts` moves non-boss enemies beyond 1360 units to the ring ahead of the player every 0.5 s, from `rng.fork('relocate')`. Snapshot fields `enemies` (count) and `enemyPositions` (`[uid, type, x, y]`); `determinism.test.ts` proves the same seed gives the same positions.
  - Weapons (#10): `shared/src/content/weapons.ts` holds `WEAPONS` (full stats per level, `maxLevel` 8, `levelText`, `assetId`/`iconId`) and `WEAPON_LIST`; `MAX_WEAPON_SLOTS` is 6. `worker/game/weapons/` holds `owned.ts` (`world.weapons`, index = slot; `addWeapon`, `levelUpWeapon`, `grantNextWeapon`), `system.ts` (`weaponSystem`: each weapon's cooldown, then a burst of `amount` shots 0.1 s apart, each calling its pattern's `fire(ctx, w, lv, shot)`), `context.ts` (`WeaponContext`: player, enemy grid, `weaponRng = rng.fork('weapons')`, `spawnProjectile`, `spawnFx`, `damageEnemy`) and `patterns/<pattern>.ts` registered in `patterns/registry.ts` (`addWeapon` throws in dev for a pattern without a module). `game/combat.ts` `damageEnemy` lowers HP, flashes, knocks back by `1 - knockbackResist` and only marks the dead bit; `cleanupSystem` (last) removes dead enemies backwards with one `enemyKilled` event and one kill each, so later consumers of `enemyKilled` (gems, #11) go after it. `game/projectiles.ts` (cap `PROJECTILE_CAP`, a 4-UID hit ring with `hitCount`) and `game/fx.ts` (64 short-lived effects) own their stores; their pools (300 `weapon.magicWand`, 64 per effect asset) are created once in `createGameView` and passed to `createWorld` like the enemy pools. Snapshot fields `projectiles` (count) and `weapons` (`{ id, level }[]`); `kills` rises.
- **Screens (ADR 0009, #9):** `main/app.ts` is the only code that mounts screens: a pure `reduce(state, event)` (`title`, `playing` with `paused`, `results`) plus `effects`, which map transitions to the worker messages `startRun` (fresh seed from `crypto.getRandomValues`), `pause`, `resume` and `endRun`; the worker answers `gameOver { stats }`. Screens in `main/ui/` (`title.ts`, `pause.ts`, `results.ts`) export `mount(root, props): Screen` with `update`/`unmount`, build elements with `h(tag, attrs, children)` from `ui/dom.ts` (text only through `textContent`) and use `menuKeys` (arrows/WASD move focus, Enter activates); styles are `ui/styles.css`. Escape while playing toggles the pause; hiding the tab while playing pauses and the overlay stays until Resume. The worker starts no run on boot. Screen tests run under `happy-dom` (`// @vitest-environment happy-dom`, a client devDependency).
- **Thread messages (ADR 0004):** `client/src/protocol/worker-messages.ts` holds `MainToWorker`, `WorkerToMain`, `DebugCommand` and `LevelUpOption`. Every `switch` on a message `type` or `kind` is exhaustive and ends in `assertNever` (`protocol/assert-never.ts`). Browsers missing `transferControlToOffscreen`, WebGL 2 on `OffscreenCanvas` or module workers get a DOM message instead of the game (`main/support.ts`; `?forceUnsupported=<name>` in dev).

- **Test bridge (#31, dev and e2e builds):** `main/test-bridge.ts` exposes `window.__vsTest` (`snapshot()`, `waitFor(predicate, ms)`), which asks the worker over the `testSnapshot` messages (`TestSnapshotRequest`/`TestSnapshotReply`, filtered out before both exhaustive switches) and returns a flat `GameSnapshot` (`WorkerSnapshot` plus `ready`, `buildRev`, `state`). It only reads. Later issues add fields by name with `registerSnapshotField(name, read)` (`worker/test-bridge.ts`) or `registerMainSnapshotField` (main thread), never by editing the bridges. Calls are wrapped in `if (import.meta.env.DEV || import.meta.env.MODE === 'e2e')`; `verify:launch` serves `--mode e2e`. `__VS_BUILD_REV__` (`vite.config.ts`, `protocol/env.d.ts`) is the git revision at server start. The run registers `timeS` (`world.time`, replacing the base steps-since-boot value) and `player` (`readPlayerSnapshot` in `worker/game/snapshot.ts`: `x`, `y`, `facingX`; later issues add fields there) (#7). Playwright lives in `e2e/` (root tsconfig reference, so `tsc -b` and ESLint cover it), the scripts in `scripts/verify/`. `verify:e2e` consumes `--issue <N>` and `--with-server` and forwards remaining arguments unchanged to Playwright. - **XP and level-up (#11, ADRs 0004, 0008):** `gemDropSystem`, `gemSystem` and `levelSystem` run right after `cleanupSystem`. Gems (`worker/game/gems.ts`) live in a store of `GEM_CAP + 1` slots drawn by `GEM_ASSETS` pools in the `pickups` layer (created in `createGameView`); drops beyond `GEM_CAP` add their value to one red merge gem (`world.mergeGemUid`), so no XP is lost. `levelSystem` moves XP into levels and raises `world.pendingLevelUps`; while it is above 0 `world.step` does nothing. `createLevelUpFlow` (`worker/game/level.ts`) pauses the loop after such a step and posts one `levelUp { level, options }` at a time (`buildLevelUpOptions`, `rng.fork('levelup')`, a heal when nothing is left, never gold); `levelUpChoice { index }` applies it and posts the next or resumes. The loop stops stepping inside a frame once a step pauses it. On the main thread the `levelUp` app state mounts `ui/levelup.ts` (keys 1–3, arrows/WS, Enter; Escape and a hidden tab do nothing), with icons from `ui/asset-url.ts` (`loadAssetUrls`, manifest-validated URLs, magenta box without art). The HUD draws `ui.xpBar` across the top with a fill and `Lv n`; `fx.levelUp` is an effect whose Lottie restarts when its pooled paint is acquired (`AssetLibrary.restart`). Snapshot fields `gems`, `gemPositions` and `player.level`/`player.xp`.
- **Multiplayer (ADRs 0005, 0006, 0014):**
  - Each player simulates their own world, and worlds are never synchronized.
  - The server handles rooms (6-character codes, nicknames), match start (seed), status relay (at most 4 Hz), interference routing and the result. WebSocket upgrades happen only on `/ws`.
  - The last survivor wins:
    - when several players die within 100 ms (server time), it is a draw;
    - a tab hidden for 30 seconds forfeits;
    - at the time limit the match ends and kills decide it, with no Death;
    - the server ends every match by itself at `startAt` + 900 s + 10 s grace (#60): players whose socket is closed then, even inside the 10 s disconnect grace, die at that instant and lose (ADR 0014); the others who reported neither `died` nor `survived` count as survived with their last relayed kills.
  - Protocol types live in `shared/src/protocol.ts` (#18): the constants (`PROTOCOL_VERSION`, room-code alphabet, `STATUS_MIN_INTERVAL_MS`, `DISCONNECT_GRACE_MS`, `SIMULTANEOUS_DEATH_WINDOW_MS`, `AFK_FORFEIT_MS`, `MATCH_TIME_LIMIT_S`, `MATCH_DEADLINE_GRACE_S`, `MAX_MESSAGE_BYTES` and others), the `ClientMessage`/`ServerMessage` unions, the hand-written validators `parseClientMessage`/`parseServerMessage` (exact fields, no extras) and `normalizeNickname`. The client's first message is `hello { v }`; a wrong version or any other first message gets `versionMismatch` and a 1008 close. In-match messages that arrive late (after `finished`, or from an eliminated player) are dropped, never errors.
  - Server modules (`packages/server/src/`): `index.ts` (`startServer(config)`: `/healthz`, the `/ws` upgrade with the Origin allow-list and the 10-per-IP cap, the 15 s heartbeat), `connection.ts` (per socket: token bucket, size check, `try` parse, validation and the hello gate before anything reaches the registry; one `error` per violation, the second closes with 1008), `rooms.ts` (`RoomRegistry`: lobby, countdown, playing, finished and back to lobby after 5 s; status throttling, interference routing, the win rule, AFK, disconnect and match-deadline timers; no I/O, injected clock, timers and RNG), `limits.ts` (`TokenBucket`, `ConnectionCounter`, `JoinLockout`, `clientIp` with `TRUST_PROXY`) and `code.ts` (room codes from `crypto.randomInt`).
- **Content (ADR 0008):** characters, weapons, passives, evolutions, enemies, waves and pickups are data in `shared/src/content/`. Systems interpret the data; each weapon's behaviour is chosen by its `pattern` field. Enemies are `ENEMIES`/`ENEMY_LIST` in `content/enemies.ts` and the stage is `STAGE` (15 one-minute waves over 900 s) with `validateStage` in `content/stage.ts` (#8; initial values, untuned against footage). ADR 0008 sets8 weapons with evolutions,8 passives and1 stage, with no gold, unlocks, relics, shops or arcanas. XP: `xpToNext` and `gemTier` in `content/xp.ts`, magnet, choice and heal constants in `content/constants.ts` (#11; initial values, curve **[unverified]**). ADR 0016 extends the originally three-character art roster to four approved identities; #14 will implement their character data/stats and selection.
- **Assets (ADRs 0007/0016):**

When text and footage disagree, footage wins. Record new observations, with their source, in that file in the same PR. Facts marked **[unverified]** must be checked before you rely on them.
