# impact-check

Rules: `.claude/rules/verification.md`. Listing callers is not the job; grep does that in seconds. The job is the breakage grep will not show you. Do not trust a write-up that merely sounds right: find the one or two facts the change's safety depends on, and prove them by running code.

## Where breakage hides in this project

Check each of these that the change touches:

- **Thread boundary (ADR 0004):** messages in `packages/client/src/protocol/worker-messages.ts`. Both the sender and the receiver must handle a changed shape, and nothing may cross the boundary per frame per entity.
- **Dev debug tools (#2):** `DebugCommand` kinds and the reserved key codes in `CLAUDE.md`'s table; `registerDebugKey`, `registerDebugHandler` and `registerPerfStat` callers. A call outside `if (import.meta.env.DEV)` ships debug code to production, and `pnpm build` then fails in `check-prod-bundle.mjs`.
- **Test bridge (#31):** the `testSnapshot` messages in `worker-messages.ts` (`TestSnapshotRequest`, `TestSnapshotReply`, filtered out before both exhaustive switches inside the dev/e2e guard) and the `WorkerSnapshot` / `GameSnapshot` shape. Fields registered by name with `registerSnapshotField` (worker) and `registerMainSnapshotField` (main thread) are read by `e2e/` specs and the `verify-game` feature files as strings: renaming or reshaping one, or changing the worker state behind it, breaks those journeys without a type error. Every bridge call stays inside `if (import.meta.env.DEV || import.meta.env.MODE === 'e2e')`; `pnpm build` runs `scripts/verify/check-prod-bundle.mjs`, which fails on `__vsTest`, `__vsDebug`, `testSnapshot` or `togglePerfOverlay` in `packages/client/dist`.
- **WASM, font and CSP delivery (#2, #46):** `/thorvg/thorvg.wasm` (the `copyThorvgWasm` plugin and `initThorVG`'s `locateFile`), `font.hud` in `assets/manifest.json` (resolved and fetched by `initThorVG`, which sets the live binding `HUD_FONT`; ADR 0013), and the preview CSP in `packages/client/vite.config.ts`, which mirrors ADR 0011 plus `worker-src blob:` for the support probe. Code that reads `HUD_FONT` before `initThorVG` resolves gets `'default'`.
- **Network protocol (ADRs 0005, 0006):** `packages/shared/src/protocol.ts` (message unions, `parseClientMessage`/`parseServerMessage`, `normalizeNickname`, the timing constants), the server's `connection.ts` gate and `rooms.ts` registry, rate limits and size limits, and the protocol version. An old client against a new server must fail cleanly (`versionMismatch`, 1008). `packages/server/scripts/ws-hello.mjs` hard-codes the version, and `verify-game/features/room-server.md` drives messages by their string `type`: a renamed message or field breaks both without a type error. The client's `main/net/client.ts` (#19) consumes `ServerMessage` through `parseServerMessage`, and the entry and lobby screens map `ErrorCode` strings to fixed messages (`entryError`, `LOBBY_ERRORS`): a new error code shows the generic message until it is mapped. `features/lobby.md` reads the `state` names `multiplayerEntry` and `lobby`.
- **Content data (ADR 0008):** IDs referenced across characters, weapons, evolutions, passives, waves and pickups, plus the debug keys that grant them.
- **Asset IDs (ADR 0007):** `assets/CATALOG.md`, `assets/manifest.json`, generated `ASSET_IDS`/`ASSET_SIZES` from `scripts/assets-sync.ts` (`pnpm assets:sync`), drawable-versus-font entries, the gallery/snapshot consumers (`assets`, `gallery`, `galleryPreview`), and the mass-art budget. `packages/shared/src/assets-catalog.test.ts` (#5) fails when the catalog and manifest ID sets differ, a file breaks the naming rule in `assets/README.md`, a mass SVG exceeds the budget, or any asset carries scripts, handlers, external references or Lottie expressions: renaming a file or adding an ID without art breaks `pnpm check`.
- **Frame loop and pools (ADRs 0003, 0004):** allocation per frame, Paint creation or disposal per frame, pool sizes, `shared/src/content/constants.ts` caps, stable UID exhaustion, swap-removal binding columns and unbind-before-remove, new-run `PaintPool.releaseAll()` then `Store.clear()`, the numeric `init.debug.stress` flag, the hidden-tab loop, and the 120-step cap. Stress snapshots read actual entities/Paints/churn; pinned ThorVG wrapper allocations are separate from owned loop allocations.
- **Per-step events and run lifecycle (#9):** `world.events` kinds (`playerHit`, `enemyKilled`) are read by later systems in the same step only, since the queue clears before the first system; a system placed before the one that pushes never sees the event. `world.state === 'dead'` stops stepping, and `startRun`/`endRun` reuse the `GameView` paints: new per-run paints must be created in `createGameView`, never in `createWorld`. The `state` snapshot field and the screen names in `main/app.ts` are read as strings by `e2e/` and the feature files.
- **Weapons and combat (#10):** `WeaponPattern` values in `shared/src/content/weapons.ts` must each have a module in `worker/game/weapons/patterns/registry.ts` (`addWeapon` throws in dev otherwise, production silently never fires); `PROJECTILE_ASSETS` and `FX_ASSETS` order the projectile and effect pools (`poolId`), so append only. Enemies die only through the dead bit and `cleanupSystem`, which must stay the last combat system: a system that removes enemies itself, or reads `enemyKilled` before the cleanup, double-counts or misses kills. Since #13 the enemy store's hit-time columns `hitT0`..`hitT5` are indexed by weapon slot (`OwnedWeapon.slot`): there must be one per `MAX_WEAPON_SLOTS` (`hit-times.test.ts`), and anything that reorders or replaces `world.weapons` (#15's evolutions) must keep each weapon's `slot`. Projectile `motion` kinds are handled only in `projectileSystem`'s `steer`; a new kind needs its branch there.
- **XP and level-up (#11):** `world.pendingLevelUps > 0` freezes `world.step`, and the worker loop stays paused until every `levelUpChoice` is answered; the `levelUp`/`levelUpChoice` messages and the `'levelUp'` value of the `state` snapshot field are read as strings by `e2e/` and the feature journeys. Any journey or test that plays a run for more than a few seconds levels up and must answer the dialog (key `1`, or `stepAnsweringLevelUps` in `worker/game/test-level-ups.ts`), or it waits forever. `GEM_ASSETS` order is the gem `tier` and pool index, and `FX_ASSETS` now ends with `fx.levelUp`.
- **Player stats (#12):** `player.stats` is one preallocated `StatBlock` rebuilt only by `recomputeStats` (`worker/game/stats.ts`); code that changes the inventory or a modifier list (`characterModifiers`, `runModifiers`, `world.passives`) and does not call it leaves the stats stale with no error. Weapon numbers reach the patterns only through `applyStats` in `weaponSystem`, so a pattern that reads `w.def.levels` directly ignores every passive. The card kinds `newPassive`/`upgradePassive` and the `passives`/`stats` snapshot fields are read as strings by `e2e/` and the feature journeys, and `answerLevelUps` (key `1`) may now pick a passive.
- **Characters (#14):** `CHARACTERS` ids are matched as strings by the `startRun` message, the `characterId` snapshot field and the feature journeys; `startingWeaponId` must be in `WEAPONS` and each `spriteId` needs a `player.<id>` pool, created in `createGameView`. `createWorld` with no id plays the default Warden, whose modifiers (+20 Max HP, +1 armor, −5% move speed) change every base number a test or journey reads: tests of base mechanics use `createBaseWorld`, and journeys that start through the title pass the character step (`startRun` in `e2e/helpers.ts` presses Enter twice).
- **Bosses, elites, chests and evolutions (#15):** `world.chestRewards` freezes `world.step` like `pendingLevelUps`, and the worker loop stays paused until `chestClosed`; the `chestOpened`/`chestClosed` messages, the `'chest'` value of the `state` snapshot field and the `chests`/`chestPositions`/`bosses` fields are read as strings by journeys. Every enemy radius read must go through `enemyRadius(cols, i)` (the `scale` column), and `MAX_ENEMY_RADIUS` is computed from `ENEMIES` and `ELITE.scale`: a new enemy is safe by construction, a radius read from `ENEMY_RADIUS` directly misses elites. Patterns draw `w.def.assetId`, so a new evolved weapon's art must be in `PROJECTILE_ASSETS` or `FX_ASSETS` (or the view's book and aura pools); evolutions replace `def` in place and keep `slot`. `WEAPON_LIST` must never list an evolved weapon.
- **Stage, finale and run summary (#17):** `ENEMY_LIST` is append only (the `type` column and the enemy pools index it). `STAGE.durationSec` must equal the protocol's `MATCH_TIME_LIMIT_S` (`stage.test.ts`), which the server's match deadline uses. `world.state` is `'running' | 'dead' | 'ended'` (a `finale: 'end'` run), and `world.cleared` stops the spawner and the stage events. Every `damageEnemy` call passes its `source` (the weapon slot, or -1) and every `ProjectileOptions` its `weaponSlot`, or the results screen's per-weapon damage is wrong with no type error if a slot is guessed. `spawnBoss` and scheduled elites evict the farthest normal enemy at the cap (`makeRoomForEnemy`). The `cleared`, `eventsFired` and `debugInvulnerable` snapshot fields and the results DOM (`data-stat`, `data-list`) are read as strings by journeys.
- **Determinism:** seeded RNG streams (`rng.fork`). A new random call in the wave path changes both players' schedules.
- **Rendering cost:** vector complexity, the number of Paints, and `update()` time. Compare with ADR 0003's numbers.
- **Server in Docker (ADR 0010):** env vars, ports, `.env.example`, `compose.yaml` and the `Dockerfile`; the `@vs/shared` `exports` conditions (`development` source for dev and tests, `default` compiled `dist` in the runtime image); and the CI `server image` job, which builds the `runtime` image and checks `/healthz`, health and the `node` user whenever the server, `shared`, Docker files, the lockfile or `.nvmrc` change.
- **Security (ADR 0011):** user data reaching the DOM, new dependencies, CI permissions.
- **Docs that go stale (`docs-sync.md`):** `CLAUDE.md` commands and architecture, and the verification map.
- **Workflow and CI (ADR 0015):** rules, skills and `CLAUDE.md` that reference each other by name or step number, and the CI `repo rules` and `PR rules` steps that grep them. The CI job `name:` values in `.github/workflows/ci.yml` are the required status checks of the `main` ruleset (`.github/rulesets/main.json`), matched as strings: renaming or removing a CI job makes every PR unmergeable. Update the ruleset JSON in the same PR, keep `scripts/github/check-ruleset.mjs` (run in `repo rules`) green, and have a maintainer re-run `scripts/github/apply-ruleset.sh` after the merge. `.github/workflows/pr-feedback.yml` (comments on red or stale PRs, runs from the default branch) and `.github/workflows/post-merge.yml` (`status:done`, unblocking) never merge; GitHub's native auto-merge does.

## Scope mode (before coding, from issue-start)

1. Read the issue's implementation plan and the code it will touch, including how the touched code is used today.
2. Write down three things:
   - **Changes:** the symbols, messages, data and files that will change, including behaviour the plan leaves implicit.
   - **Consumers:** for each item, every place that reads or depends on it. Follow what grep misses: JSON or message shapes, IDs used as strings, generated files, the other thread, the server.
   - **The one safety fact:** the single fact the change is safe because of, for example "the new `levelUpOffer` field is optional and the only reader is C6's screen".
3. If the consumers reach beyond the issue's scope, update the issue body (or split it) before coding.
4. Post it as the issue's start comment (`issue-start` step 6), written to a file and passed with `--body-file`. Keep it short: three headed bullet lists, no prose.

## Proof mode (before the PR, from issue-finish)

1. Re-read the diff against the scope notes. Anything changed that was not in scope gets the same consumer analysis.
2. Push the safety fact as far down the proof levels as it will cheaply go, and reach at least **level 4**: a Vitest test or a small script under `scripts/verify/` that calls the real code and fails loudly if the fact is wrong. Run it and keep its output in `verification/issue-<N>/`.
3. Rate each remaining risk by likelihood and cost. Keep the confirmed ones, and list what you checked and cleared, citing a real `file:line`. A search that finds nothing is an answer. Never invent a caller.
4. For user-visible effects, hand off to `verify-game` for level-5 proof.
5. For a large or cross-cutting change, run this mode in two independent subagents, give neither the other's conclusion, and merge their findings.

## Report (goes in the PR body under "Impact")

- **What it does:** including the part that is not obvious.
- **Safety fact:** the fact, the proof level it reached, and the proof (the command and its output). Write "unproven" if it is unproven.
- **Risks:** how each would break, `file:line`, likelihood and cost, and how to check it.
- **Cleared:** what was checked and why it is fine.
