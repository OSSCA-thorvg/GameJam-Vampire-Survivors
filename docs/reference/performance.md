# Performance reference: entity caps and the Lottie question

Measurements behind the entity caps in `packages/shared/src/content/constants.ts` (ADR 0007, retained by ADR 0016) and the answer to "can each enemy be a Lottie?" (#22). Re-measure with the commands below whenever the art, the renderer or ThorVG changes, and add a dated table here.

## How to measure

```sh
pnpm --filter client exec vite build --mode perf          # minified build that keeps the stress scenarios
pnpm --filter client exec vite preview --mode perf        # serves it (add --port <free> --strictPort if 4173 is taken)
```

Open `/?stress=<name>&perf` in a headed browser on a real GPU, one tab, nothing else GPU-heavy running. The scenario warms up for 5 s, measures for 60 s, then logs `[stress] result {json}` and shows the same JSON with a **Copy results** button; every 10 s, and on any uncaught worker error, it also logs `[stress] progress {json}` (#119). Run every scenario 3 times and record the median of the per-run values. The overlay (`?perf`, also in the normal production build) shows the same timings live.

The committed harness does the runs (#119; Playwright's browsers, `pnpm exec playwright install chromium firefox webkit` once; `chrome` uses the installed Chrome):

```sh
node scripts/perf/measure.mjs --browser <chromium|chrome|firefox|webkit> --base http://localhost:4173 \
  --out verification/issue-<N>/results.jsonl --runs 3 --max-load 4 [--max-wait <s>] [--headed] <scenario...>
node scripts/perf/summarize.mjs verification/issue-<N>/results.jsonl   # the table below, plus the GPU strings seen
```

It runs run 1 of every scenario, then run 2, and so on, each attempt in a fresh browser that it kills afterwards. Browsers run headless by default: on macOS headless Chrome (`--browser chrome`, ANGLE Metal), Firefox and WebKit render on the real GPU (each record's `gpu` says which renderer ran; Playwright's own `chromium` is SwiftShader headless, so do not measure with it headless). `--headed` opens Chrome's window off-screen at a fixed 1280×800 (never in front, never minimized, because macOS throttles occluded windows); Firefox and WebKit cannot be placed off-screen. A run gets at most 2 attempts, 120 s each. `--max-load 4` waits for a 1-minute load average below 4 before each attempt (macOS or Linux only), at most `--max-wait` seconds (600 by default), then runs anyway and records `loadGateMet: false`; every record keeps `loadBefore` and `loadAfter`. A timed-out attempt leaves a full-page screenshot and a line in `<out>-failures.jsonl` with the console errors, the last progress line and the last 50 console lines; the harness exits 1 when a run fails both attempts.

### Reading the numbers

- Every scenario in every browser holds the display rate: frame median 16.7–17 ms and p95 17.5–19 ms on a 60 Hz display, well under the 20 ms criterion. The single higher per-run p95 values (21–22 ms, WebKit) come with the busiest load averages; maxima of 20–75 ms are isolated hitches from the shared machine. One Chrome `lottie-enemy` run reported an 8.4 ms median: the window was on a 120 Hz display for that run.
- Worker CPU per frame stays small and grows linearly with enemies: in Chrome, sim + transform + update + render is about 0.6 ms at 400 enemies, 1.0 ms at 800 and 1.5 ms at 1200 (Firefox 1.2 / 1.3 / 2.5 ms, WebKit 1.2 / 2.0 / 2.6 ms). Even a CPU four times slower would spend about 6–10 ms at 1200 enemies, inside the frame. The GPU's share is not visible in these timings (`render()` returns before the GPU finishes) and is what a reference laptop must show.
- `projectiles-max` peaked at only 12 live projectiles in this pass: the 300 enemies surround the player, so most shots hit in the step they are fired. #119 added an emitter that keeps the store filled; its results are below.
- `gems-flood` holds 1001 gems (1000 normal plus the merge gem) at the display rate; paints grew from 2938 to 3538 as the blue pool grew past its prewarm.

### projectiles-frozen stall

**Case (d): the stall does not reproduce.** Decision rule from #119 step 7: no error was captured (`errors` empty in all records, no failure record, no `stressProgress` with `error` set), every run completed, and `steps / (60 × durationS)` was 0.9998, 1.0000 and 1.0000 in the three Chrome runs (0.9994–1.0002 in WebKit). The progress lines rose steadily every 10 s (for example run 1: 604, 1203, 1803, 2403, 3004, 3603 steps at 10–60 s; simulated time equal to wall time). The frozen run's frame median (16.6 ms) equals `projectiles-max`'s, so case (c) does not apply either.

The runs were **not** on an idle machine: `loadGateMet` is `false` in all three Chrome runs (load 7.1, 6.6 and 4.4 before them), and they ran headless rather than headed. Issue 22's stall happened in headed Chrome at a load average of 27 with parallel agents; with the same scenario committed and running cleanly here at load 4–11 (WebKit run 1 started at 10.7), it is recorded as a load artefact of that session, not a defect. The peak of 61 live projectiles matches the 49–61 issue 22 saw. Repro: `node scripts/perf/measure.mjs --browser chrome --base <perf preview> --out <file> --runs 3 --max-load 4 projectiles-frozen`.

Error reporting was proven in a real run too: in headless Chrome on `?stress=projectiles-max&perf`, an error thrown and a promise rejected inside the game worker 25 s in each produced `[stress] progress {..., "error": "Error: issue-119 probe: ..."}` on the main-thread console, next to `[vs] game worker error: Uncaught Error: ... at :3:13`; the scenario kept running and posted its result.

## Decision: caps stay at 400 enemies, 600 projectiles and 400 gems

The cap rule is the largest count whose p95 frame interval stays at or below 20 ms **on the reference machine in Chrome**. That machine was not measured, so ADR 0007's rule ("raise them only with a measurement on a mid-range laptop") keeps the caps where they are. The development machine confirms they are safe there with a large margin: 1200 enemies, 1001 gems and the max-weapon load all held p95 ≤ 19 ms in three browsers. The measurements confirm ADR 0007; no ADR is added. The wave table's peak of 300 live enemies (#17) is below the enemy cap, so no mass art needs simplifying.

Pool prewarm retune from the #11, #13 and #17 findings: `gem.blue` is prewarmed to `GEM_CAP` (400, was 200) so a full screen of the commonest gem never grows the pool mid-run, and `fx.levelUp` to 4 (was 2) for back-to-back level-ups; the view now creates 2938 Paints at boot (was 2736). Enemy pools stay at 200 per type: the whole boot, including those Paints, finishes in about 0.2 s.

Gem prewarm retune for #151: past the cap the overflow recycles the farthest (mostly blue) gem into each new drop, so green and red drops keep replacing blue ones and their pools would grow mid-run. `gem.green` is prewarmed to `GEM_CAP` (400, was 50) and `gem.red` to `GEM_CAP + 1` (401, was 50, one more for the merge gem); the view now creates 3666 Paints at boot in the fake view of `view.test.ts` (was 2965). Measured on the development machine (headless Chrome, `enemies-400`, `perf` build, 3 alternating runs each, load average 11–26, so `loadGateMet` false): `loadMs` (navigation to `assetsReady`) 500 ms on main against 536 ms with the change (mean; 461–551 against 517–571), frame median 16.67 ms on both and p95 22.53 against 22.80 ms, `canvas.update()` 0.9 ms and `render()` 0.4–0.5 ms on both (2026-11-10).

## The Lottie-per-enemy question

**Supported, and the recommended approach is one pooled `LottieAnimation` per enemy** (`PaintPool` over `AssetLibrary.create`, advanced by `AssetLibrary.tick`). 400 animated `enemy.lottieTest` instances held the display rate in all three browsers (Chrome p95 17.7 ms). The cost moves into ThorVG: `canvas.update()` rises to about 1.1 ms per frame (Chrome; 1.4 ms in Firefox and WebKit) from about 0.1 ms for 400 static PNG enemies, and ticking the 400 animations costs about 0.36 ms per step.

**Sharing one animation and duplicating its Picture for every enemy every frame works in webcanvas 1.1.3** (the copies show the shared frame), but it is not recommended: it is no cheaper (transform 1.07 ms plus update 1.26 ms per frame in Chrome, against 0.04 + 1.10 ms per enemy), it creates and disposes 400 Paints per frame, which ADR 0003 forbids, and it gave the worst hitches (max 25.6 ms in Chrome, 48 ms in Firefox).

The ADR 0007 Lottie rule stays as it is ("Lottie is for a few on-screen instances"): moving mass enemies to Lottie should wait for the reference-laptop measurement, because its `update()` cost is about ten times that of static art.
