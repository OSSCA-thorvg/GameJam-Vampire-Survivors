# 0006. WebSocket relay server for rooms and match events

- Status: Accepted
- Date: 2026-11-07

## Context

- REQUIREMENTS 13: multiplayer needs a connection; use something other than sockets if possible.
- REQUIREMENTS 14 and 15: players enter a nickname and join a room by code.
- WebRTC peer-to-peer was offered and still needs a signaling server to exchange connection details. Given separate worlds (ADR 0005), the traffic is a few small events and status updates per second, so peer-to-peer brings no benefit. The requester chose a WebSocket server on 2026-11-07.

## Decision

- `packages/server`: Node + `ws`, holding rooms in memory. No database.
- **Room code:** 6 characters from an alphabet without look-alike characters (`ABCDEFGHJKMNPQRSTUVWXYZ23456789`), generated by the server, unique among live rooms.
- **Nickname:** 1–12 characters after trimming, unique within a room.
- The room creator is the host and starts the match once every player is ready. The server picks the seed and the start time and broadcasts them.
- The server is authoritative for room membership, match start, interference routing and the final result. It is not authoritative for gameplay.
- **Protocol:** JSON messages, a discriminated union on `type`, defined once in `packages/shared/src/protocol.ts`, with a protocol version sent in the first message. The server validates every incoming message's shape and size and drops the connection on violation.
- **Status updates:** each client sends HP, level, kills and alive state at most 4 times per second. The server relays them to the other players in the room.
- **Disconnects:** a player who disconnects during a match is treated as dead after a 10 second grace period. Rooms are deleted when empty.
- The server exposes `GET /healthz`, accepts WebSocket upgrades only on the `/ws` path, and listens on the `PORT` environment variable (default 8787). The client reads the full URL from `VITE_SERVER_URL`, for example `ws://localhost:8787/ws`.

## Alternatives considered

- **WebRTC with the public PeerJS server** — no server to run, but depends on a free public service and still exchanges the same messages.
- **Cloudflare Workers with Durable Objects** — no process to run, but adds a vendor account and its own API.

## Consequences

- One small Node process must be deployed. The hosting target is not decided yet and is tracked as its own issue.
- The browser connects with plain `WebSocket`, so the client has no networking dependencies.
- In-memory rooms are lost on restart, which is acceptable for a jam.
